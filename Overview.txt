RESUME-PARSER  |  PROJECT & DEPLOYMENT BLUEPRINT

1. Executive overview

Resume-Parser helps a recruiter compare one or more PDF resumes against a job description. The AI model interprets semantic relevance and proposes structured assessments. Python validates those assessments, verifies evidence, and calculates the final score. The system must not invent skills, qualifications, experience, quotations, or page numbers.

The API should accept work quickly and return HTTP 202 Accepted with a job ID and per-job access token. A separate worker atomically claims queued jobs from PostgreSQL, processes documents, persists validated results, and marks each job completed or failed. The browser polls a protected status endpoint and renders the result when ready.

Principle

Requirement

Evidence first

Every displayed quote must be traceable to extracted resume text; page references must be grounded in page-level extraction.

Deterministic scoring

Python calculates final score from validated category values and documented weights; the LLM does not directly set the final score.

Durable jobs

Queued work and status survive process restarts; expired leases can be reclaimed safely.

Least privilege

Candidate data and secrets are not exposed to browser code, logs, or public storage.

Honest failures

Provider, parsing, and validation failures become explicit errors, never fabricated fallback scores.

Human oversight

The score is decision support, not a hiring probability or substitute for human review.

2. Product goals and user workflow

2.1 Primary workflow

Recruiter opens the home page.

Recruiter pastes a job description or uploads a job-description PDF.

Recruiter uploads one or more resume PDFs within configured count, size, and page limits.

Frontend performs early validation; backend independently validates every input.

API persists a queued job and inputs, then returns 202 with job ID and access token.

Browser polls the protected status endpoint with the token in an Authorization header, never in the URL.

Worker atomically claims the job, parses PDFs, calls the AI provider, validates evidence, calculates scores, and persists the result.

Browser displays the scorecard when completed, or a sanitized failure and retry/new-analysis option.

Scheduled cleanup removes expired data according to retention rules and never deletes active jobs.

2.2 Feature overview

Feature

Expected behavior

JD input

Pasted text or one PDF; reject empty or unreadable input.

Multiple resumes

Asynchronous jobs

Dry-run first; delete only confirmed expired records and orphaned files.

5. Scoring and evidence policy

AI proposes semantic category assessments; Python validates them, checks evidence, normalizes applicable weights, and computes the final score. Never trust an LLM-generated total without recalculation.

Category

Initial weight

Assessment

Required skills

30%

Required skills and justified equivalent terminology.

Experience and projects

25%

Relevant tasks, projects, accomplishments and scope.

Responsibilities/capabilities

20%

Evidence mapped to actual job responsibilities.

Qualifications

10%

Relevant stated education/certifications, where job-related.

Evidence strength

15%

Specificity, traceability and support for claims.

These weights are starting assumptions, not validated hiring science. Calibrate with qualified reviewers and job-specific evaluation. Do not use protected or irrelevant characteristics.

Validate all category scores are finite and within the documented range, e.g. 0–10.

With weights represented as fractions, contribution = category_score × normalized_weight; total remains on a 0–10 scale.

Normalize only categories genuinely not applicable. Do not label missing evidence as inapplicable just to improve a score.

Calculate percentage as final score × 10 with one documented rounding rule.

Avoid double-counting one achievement across categories without distinct supporting evidence.

Distinguish 'not found in extracted text' from 'candidate lacks the skill'. Poor extraction should reduce confidence, not prove inadequacy.

Provider/schema/evidence failures must not silently fall back to keyword scores.

5.1 Evidence validation

Preserve page-level text and source offsets where possible.

Normalize whitespace, Unicode ligatures and extraction artifacts while retaining a mapping to original text and page.

Fuzzy matching is a verification aid, not permission to invent an exact quotation.

Reject or mark uncertain claims that cannot be located in extracted text.

Treat document text as untrusted data; embedded prompt instructions never override system instructions.

Display page numbers only when provenance is reliable.

6. Data model and durable job lifecycle

6.1 Suggested Render Postgres tables

For a strict Render-only setup, adapt the Supabase-specific schema to ordinary PostgreSQL. PostgreSQL supports functions and row locking, but Supabase Storage and Supabase-specific APIs do not appear automatically on Render.

Table

Purpose / suggested fields

screening_jobs

UUID ID, status, created/updated/started/completed timestamps, attempts/max_attempts, lease owner/expiry, safe error code/message, result JSONB, retention/deletion timestamp.

screening_inputs

Job ID, input type, sanitized filename, content type, size, PDF bytes or protected storage reference, checksum, timestamp.

job_access_tokens

Job ID, token hash, created/expiry/revoked timestamps; never store raw token if a hash is sufficient.

audit_events (optional)

Minimal security events and correlation IDs; no resume text or secrets.

6.2 Atomic claim and leases

One PostgreSQL function/transaction claims a queued job using row locking such as FOR UPDATE SKIP LOCKED and changes it to processing atomically.

Record lease owner and expiry. Renew long-running leases; reclaim expired leases after a worker crash.

Bound attempts and use backoff; permanent failures should not retry indefinitely.

Persist results idempotently; guard state transitions so late workers cannot overwrite valid results.

Restrict EXECUTE on the claim function. If SECURITY DEFINER is used, set a safe search_path and qualify referenced objects.

Use least-privilege database roles for web and worker where practical.

7. Security, privacy, and file handling

Control

Requirement

Transport

HTTPS in production; no resume/token transmission over plaintext HTTP.

Tokens

Cryptographically random; hash before storage; verify against correct job; define expiry/revocation; never put in URLs/logs.

Database

Use Render internal connection URL where appropriate, least-privilege credentials, parameterized SQL and versioned migrations.

PDF validation

Signature and parser checks; cap bytes/pages/count/text/time; handle encrypted, malformed, empty and scanned PDFs.

Temporary files

Random safe names; controlled temp directory; prevent path traversal; cleanup on success/error/shutdown.

Logs

No API keys, access tokens, full resumes or full JDs. Log correlation IDs and sanitized error codes.

Rate limits

Request/upload/concurrency quotas; trust forwarded IP headers only from configured proxies.

Prompt injection

Document text is data, not instructions; enforce fixed system prompts and structured-output validation.

Retention

Document retention duration; implement deletion and monitor cleanup failures.

Hiring fairness

Use job-related criteria, human review and edge-case evaluation; never present score as final hiring decision.

8. Strict Render-only architecture

8.1 Topology

Browser --HTTPS--> Render Web Service (FastAPI + frontend)
                         |                |
                         |                +--> Hosted AI provider API (external)
                         v
                    Render Postgres <---- Render Background Worker
                         ^
                         +-------------- Render Cron cleanup

The application services and primary database can run on Render. A hosted Groq/NVIDIA model is still an external API. 'All in Render' can cover application hosting and persisted application data, but not hosted model inference unless you self-host a model.

8.2 File storage decision

Render filesystems are ephemeral by default. Persistent disks preserve files but attach to a single service instance and cannot be directly shared between separate web and worker services. For a strict Render-only MVP, size-limited PDF bytes can be stored in Render Postgres for both services to access. This increases database size and is not ideal for large workloads. Do not rely on local temporary folders as durable storage. Larger-scale storage may require an external object store or a deliberately designed shared-storage approach.

8.3 Changes from supplied tree

Current item

Strict Render-only change

supabase/migrations/*.sql

Adapt into ordinary PostgreSQL migrations; remove Supabase-only syntax.

Supabase queue RPC

Implement a PostgreSQL function on Render Postgres and call it via a DB driver.

Configure PostgreSQL roles/grants and, where appropriate, PostgreSQL RLS; Supabase-specific default roles are not automatically present.

9. Render deployment walkthrough

These are steps to perform; this document does not claim that a deployment has already been created.

9.1 Prepare repository

Push the correct branch to your Git provider and preserve existing work.

Ensure pyproject.toml and uv.lock agree; test dependency installation with the committed lockfile.

Verify the app import path, e.g. app.main:app, and static asset serving.

Add tests for uploads, polling, token authorization, worker recovery and scoring.

Keep .env out of Git; commit only placeholder values in .env.example.

For strict Render-only hosting, remove/replace Supabase DB/storage dependencies before deployment.

9.2 Create Render services

Create a Render PostgreSQL database in a region close to the web and worker services.

Create a Web Service connected to the repository using the runtime matching your project.

Use the build command appropriate for the actual packaging setup. Example only: `uv sync --frozen`, if uv and the project configuration support it.

Use a start command appropriate to the environment. Example only: `uv run uvicorn app.main:app --host 0.0.0.0 --port $PORT` if uv is installed and app imports correctly.

Create a Background Worker from the same repository, e.g. `uv run python -m app.worker`, after confirming module execution and graceful shutdown.

Create a Cron Job for cleanup if supported by the selected plan/configuration. Start in dry-run mode.

Set the web health check to /health. Liveness should not fail merely because the AI provider is temporarily down.

Represent the services in render.yaml where supported; validate the Blueprint before relying on it.

9.3 Database and migrations

Set DATABASE_URL using the Render Postgres internal connection URL for same-region services when appropriate.

Run migrations as a controlled release/one-off step; do not let each worker independently migrate at startup.

Create job/input/token tables, indexes, constraints, state transitions and atomic claim function.

Limit database privileges for web and worker; restrict claim-function execution.

Test two concurrent workers and prove the same job is not actively claimed twice.

9.5 Live deployment smoke test

Open the Render URL and verify HTML, CSS and JavaScript load.

Call GET /health and confirm no secrets or internal diagnostics are exposed.

Submit an invalid file; verify a safe 4xx response and no stuck job.

Submit a valid test resume and JD; verify 202 and token delivery.

Poll with the correct token; verify missing/wrong token is rejected.

Follow logs by correlation ID and verify queued → processing → completed/failed.

Restart the worker during a test; verify lease recovery and no duplicate result write.

Verify quotes/pages are grounded and percentage equals score × 10.

Run cleanup dry-run and review proposed deletions before enabling deletion.

Record actual tests, provider quotas, plan limits and any unresolved issues.

11. Testing and release checklist

Test area

Must prove

Parser

Valid PDFs succeed; bad signature, malformed/encrypted, oversized, page-limit and empty extraction are handled.

API

Valid input returns 202; invalid input returns proper 4xx; health check is safe.

Security

Wrong/missing/expired token denied; token absent from URL/logs; rate limits and proxy handling tested.

Worker

Concurrent claim safe; expired lease reclaimed; retries bounded; duplicate completion prevented.

Evidence

Whitespace/ligature artifacts handled; fabricated quotes and wrong pages rejected.

Scoring

Scores in range; weights normalize correctly; contributions reconcile; percentage = score × 10.

AI provider

Timeout, 429, auth failure, 5xx, malformed JSON and invalid schema produce distinct safe outcomes.

Privacy

No resume text/tokens/keys in logs; retention and orphan cleanup tested.

Deployment

Web and worker start; migrations apply; end-to-end screening succeeds on Render.

Golden dataset guidance

Use synthetic, licensed, consented, or appropriately de-identified examples. Do not commit identifiable resumes to a public repository.

Store human-reviewed acceptable score ranges and evidence expectations, not one allegedly perfect universal score.

Include equivalent skill wording, different layouts, career gaps, project-based experience, scanned/poor PDFs and missing evidence.

Separate deterministic unit tests from empirical quality/fairness evaluation. Passing math tests does not prove the model is fair.

13. Limitations and decisions

This is a project/deployment blueprint, not a verified audit of current repository contents or test results.

Render-hosted app services can still call an external hosted AI provider. Fully self-hosted inference requires a separate model-serving design.

Render filesystems are ephemeral by default. Persistent disks are single-service-instance and cannot be shared directly between separate web and worker services.

The supplied Supabase migrations/RPC/storage must be adapted to remove Supabase entirely. Deploying current code on Render alone does not remove that dependency.

Render pricing, plans, region options, database backup features and Blueprint syntax can change; confirm current options in the dashboard and docs.

Keep human review for consequential hiring decisions; the score is not a final decision or probability of hire.
